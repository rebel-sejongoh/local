feat(mcc): add an initial cut of mcc performance regression testing

## Motivation

- We don't have a framework to measure and check the performance of the code mcc compiles.

## Solution

- Each test case under `PrimitiveAuthor/mcc/tests/perf/` keeps its base code as textual assembly, with the inputs and golden the VP runs it with.
  The test case also states the same computation in kpl, for mcc to compile.
- The base code can be handwritten, generated by the rebel compute library, or authored any other way.
  The first test case, `add_elementwise`, comes from the rebel compute library's add test.
- `test_perf_vp.py` compiles every test case with mcc.
  Its VP test also runs the base code and mcc's code on the VP and checks both against the golden.
  The VP test fails when mcc's code takes more cycles than the base code times a tolerance factor.
- Each test case records the base code's cycles and its tolerance factor in `base/manifest.json`.
  A base run that no longer takes the recorded cycles fails too, so a changed VP or base code cannot shift the bound unnoticed.
- The VP is not yet reliably available on CI, so the VP test is marked `requires_vp`, mcc's pytest configuration deselects it, and no lane runs it.
  `-m requires_vp` selects it locally.

## Verification

- `uv run pytest tests` in `PrimitiveAuthor/mcc` passes, with the VP test deselected.
- With `-m requires_vp` on a dev VM, the base code and mcc's code of `add_elementwise` both match the golden.
  The base code takes 796 cycles and mcc's code 557.
- With the tolerance factor set to 0.5, the same run fails on mcc's cycles.
  Without the VP's libraries on `LD_LIBRARY_PATH`, it fails naming them.
- mcc's pre-commit checks (`moon run mcc:static-check-*`: lint, format, typecheck, lock check, cram) pass.
- Every other lane is left to CI.
